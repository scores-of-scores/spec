Start here

Version 2026-11. A short orientation to the Transcription Principles, the format evidence and the Notes for Transcribers, for people meeting them for the first time.

What this is

Scores of Scores aims to give the public domain repertoire an open, citable digital encoding. Each score is transcribed from one printed source, exactly as that source prints it, so that other people and programs can build on it without having to check it against the page first.

This repository holds the rules that make such a transcription trustworthy, the evidence of what each encoding format can express, and the profiles that record two projects' different choices over the same rules. The rules are written so that another project can adopt them and make different choices.

Who it is for

  • Transcribers and reviewers follow the rules and the local Notes day to day.
  • Editors and editorial projects build on the result. Because a transcription never chooses between readings, completes or interprets, an edition can start from a fixed, exact record and keep its own decisions separate and visible.
  • Other projects can adopt the core rules and the formats data unchanged and write their own profile.

Six ideas that explain the rest

  1. A transcription records; it does not edit. Errors in the source are kept as printed and recorded as observations, never fixed silently (read.preserve-errors, stance.judgement-stays-out).
  2. There are three tiers of decision. Transcription needs no musical judgement and no second source. Presentation is systematic, reversible and changes nothing notated. Editorial needs judgement or another source, and is not done in the transcription.
  3. Presentation choices are a closed list. Only the registered normalisations (normalise.*) are allowed, each one stated once per transcription (normalise.closed-list).
  4. When in doubt, preserve. If it is unclear which tier a decision falls in, keep what the source prints and record an observation (stance.doubt-means-preserve, declare.observations).
  5. Only a clear error can be corrected, and a test decides what is clear. The test is in the core (correct.error-test). A profile chooses whether a correction is made in the transcription or in a separate layer, and every correction is recorded (correct.in-place, correct.layer, correct.record).
  6. The format sets the limit. What a format cannot express is derived from the formats data, not asserted, and a deviation from the source is always reported (declare.report-deviations).

If you are building an edition on top of this

Start from a pinned version of the transcription, work in your own project, and record every change there, using an established scheme such as the editorial markup in MEI or TEI. The Notes in the area Editorial matters (editorial.*) say which kinds of intervention (harmonising parts, suggested accidentals, choosing between sources, dropping the source's own brackets) belong to you rather than to the transcription.

Scope of this version

Version 2026-11 covers printed sources in the KRN version of record. Lyrics, piano pedalling, articulations, repeats, rehearsal marks, hairpins, ornaments other than grace notes, and courtesy accidentals already in the source have no Note yet; for them the core rules apply unchanged. Manuscripts are out of scope.

Transcription Principles: framework

How the Principles are organised and used. Version 2026-11. Part of the Scores of Scores document set (see the README). The rules themselves are in the generated rules table; what each format can express is in Format support.

1. What this is

The Principles are a small, tool-neutral framework for a pragmatically faithful transcription of a notated source into a digital encoding. They say what a transcription must and must not do, what it must declare, and the one kind of correction that a project may allow. They are written so that another project can adopt the core and make different choices.

The format sets the limit. A transcription is made in a particular encoding format, and the Principles apply within what that format can express (stance.faithful-reading: "as exactly as the encoding allows"). What a format can express is not asserted in the rules. It is recorded as evidence in the formats data and linked to the rules it bears on (section 5). Where a detail cannot be represented, the nearest available form is used (read.ornaments-as-printed, read.ambiguous-marks); where a whole category of printed mark cannot, its treatment is derived as unsupported. This is a limit of the format, not a judgement, so it is not an editorial matter, and it changes when the format or the profile changes.

Out of scope: editorial work other than the clear-error correction of section 6 (choosing between readings, completing, interpreting, comparing sources, performance practice) and manuscripts and other special sources, which need further rules.

2. Four layers

Layer Holds Changes Where
Core The rules: what a transcription could be required to do, how rules relate (refines, exception, requires, tension), the tiers, the vocabulary Rarely core/principles.yaml, core/glossary.yaml
Formats Evidence of what four formats can express, feature by feature, with sources, linked to the rules it bears on When a format, a source or a test result changes formats/
Profile A project's choices: how strong each rule is, which rule wins in a tension, ranked aims, the format of its version of record, what is out of scope When the project decides profiles/
Local notes Tool settings, placement defaults, workflow, report format, suggestions for downstream work Often notes/registry.yaml

Where does a rule belong? If a reasonable project could reject it, it is a profile choice, not core. Even "preserve errors" is a stance, because correcting is the classic opposing view: the core defines both read.preserve-errors and correct.in-place, and each profile decides which to adopt and which wins. Local notes may narrow what the profile allows, never widen it.

3. Tiers and the boundary test

Every decision falls into one of three tiers (defined in the registry):

Tier Test Allowed in the transcription?
Transcription A competent reader could do it from the source and a stated notational convention, with no musical judgement and no second source Yes
Presentation Systematic, reversible, changes nothing notated, stated once in the report Only the registered normalisations (normalise.*)
Editorial Needs musical judgement or another source No, except a correction that passes the clear-error test and that the profile allows

Three questions, in order: 1. Does it change what is notated (a pitch, rhythm, mark or text)? If yes, it is not presentation. 2. Could it be done from the source and a stated convention alone? If yes, it is transcription; if no, it is editorial. 3. Is it systematic, reversible and reported once, and is it registered under normalise? If yes, it is presentation.

If it is unclear, treat it as editorial: keep what the source prints and record an observation (stance.doubt-means-preserve, declare.observations).

Situation Tier Handling
The source's convention makes an accidental implicit and the encoding needs it explicit Transcription Add it and mark it (declare.mark-additions)
Cut-time symbol printed Transcription Keep it (read.preserve-distinctions)
A curve may be a slur or a tie, with unclear ends Transcription The reading the convention fixes, else the nearest-endpoint slur, with an observation (read.ambiguous-marks)
One part has a different articulation from the others Editorial Keep as printed (read.consistency-by-equivalence)
A printed note appears to be wrong Editorial Keep as printed and record an observation (read.preserve-errors); correct only if the error is clear and the profile allows it (correct.error-test)
An edition beams every 6/8 bar the same way Presentation Normalise (normalise.beam-grouping)
The composer groups beams unusually in one passage Transcription Keep (read.composer-led-grouping)
An editor might add a suggested accidental (musica ficta) Editorial Do not add
Cello treble clef that sounds an octave lower than written Presentation Notate at sounding pitch (normalise.clef)

4. Anatomy of a rule

Each rule in the registry has:

Field Meaning
id <domain>.<slug>, permanent
theme A mid-level grouping within its domain (metadata, not part of the ID)
kind obligation (a do or don't) or permission (a registered normalisation or a correction)
title, statement A strength-neutral imperative; the profile supplies the strength
relations refines, exception-of, requires, tension-with, see-also
format_features Formats-data features that bear on what the rule can achieve in a given format
rationale, examples Why, and worked cases
aliases Earlier codes, for traceability
status active, proposed or retired (retired rules name replaced_by)

Domains

stance (what a transcription is), read (what is read), encode (how it is encoded), normalise (the closed menu of presentation choices), declare (what is marked, reported and recorded), correct (the clear-error test and where a correction is made and recorded). The domain is the only hierarchy in the ID. Themes are metadata, so a rule can be re-themed without a rename.

Relations

Relation Meaning Consequence
refines A more specific form of another rule Never conflicts
exception-of Limits another rule in a stated scope Wins over it in that scope, in every profile
requires Cannot be adopted without the other Checked by the build for every profile
tension-with Can pull against the other The profile must resolve every tension (checked by the build)
see-also Related None

Strengths

Set by the profile, using the BCP 14 terms (RFC 2119, RFC 8174), in capitals only where they are normative: MUST, SHOULD, MAY, OFF (not adopted; for a normalisation or a correction, not permitted).

5. Formats and derived treatments

The formats layer is a dataset of features, each answered for four formats (KRN, MusicXML, MuseScore's native format and MEI). Each cell has a status (direct, qualified, extension, workaround, unknown), a mechanism, any condition, a workaround, an evidence label (documented, inference, unverified) and cited sources. Status is a capability label and never a score; no format is ranked. A cell counts as tested only when a fixture that covers it has a recorded result for that format.

Rules link to features through format_features, and the build generates the inverse. A feature linked to a rule shows the rule IDs in the reader; the format support table shows, for each profile, whether the feature is expressible in its format.

Mark categories. Some printed marks may fall outside a format. The registry lists such categories (mark_categories), each linked to a feature. The treatment in a profile is derived from the status of that feature in the profile's format:

Status in the profile's format Treatment
direct, qualified Transcribed (a qualification is reported)
extension Transcribed if the profile accepts that extension (scope.encoding.accept_extensions); otherwise unsupported
workaround, unknown Unsupported

A profile may reclassify a category in scope.marks, with a reason. Any printed mark outside a listed category is transcribed (read.transcribe-all-marks). A project that needs another category proposes it for the registry, as for a rule. When a format gains support, the cell changes and so does the derived treatment, in a new pinned version.

The dialect is part of the profile. scope.encoding names the format, the exact dialect or version, and the extensions accepted. A profile that accepts no extension for a feature treats a feature whose status is extension as unsupported.

6. Corrections

A source error is clear only if it passes correct.error-test: (1) the printed reading is impossible under the source's own notation, and (2) exactly one minimal change makes it possible, found from the source alone. Every other error is kept as printed.

The core defines two placements and a record. A profile chooses between them, which is the main difference between positions:

Rule Meaning Strengths in the shipped profiles
correct.in-place A clear error may be corrected directly in the transcription OFF in sos-2026-11; MUST in openscore-2026-11
correct.layer Corrections that are not made in the transcription are recorded in a separate layer pinned to a transcription version MUST in sos-2026-11; OFF in openscore-2026-11
correct.record Every correction is recorded with location, printed and corrected readings, and the condition of the test that was met MUST in both

correct.in-place is in tension with read.preserve-errors, so each profile resolves it in precedence. Everything else that needs judgement stays editorial and outside the transcription. Downstream editions record their own changes in their own project, using an established scheme such as the editorial markup of MEI or TEI, pinned to a transcription version (work@version).

7. Identity and change

  • IDs are never renumbered and never reused. If a rule's meaning changes materially it gets a new ID and the old one is retired with replaced_by and a date. Editorial rewording keeps the ID.
  • Four kinds of ID share one namespace, and the build rejects a clash: rules and notes (domain.slug, area.slug), format features (fmt.slug) and fixtures (fx.slug).
  • The Principles, the formats data and the Notes use date versions (YYYY-MM), and each release has one tag and one DOI. Schemas carry their own version in their $id. Cite a rule as read.preserve-errors@2026-11, and a feature as fmt.fingering@2026-11.
  • A change to a rule, a profile choice or a format cell appears in a new dated version and is listed in CHANGELOG.md. A proposed extension is a rule with status proposed: it has no strength in any profile until it is made active in a new version. Changes are not retroactive.
  • Each transcription records principles_version, the profile it followed, the notes_version and the normalisations it applied (the sidecar; see declare.record-provenance).
  • Build. python3 tools/build.py validates every file against its schema and the links between layers, and generates the rules table, the format support table, the glossary, the Notes, the formats reader, the paper's tables, JSON files and CSV files. It fails on, among other things: a relation or format link whose target is missing, a tension without precedence, a cycle in precedence, an active rule without a strength, a rule that is adopted while a rule it requires is OFF, an accepted extension that is not an extension in the profile's format, a duplicate ID or alias, and a Note that applies a normalisation or correction that the profile does not permit.

8. Adopting the Principles elsewhere

  1. Take core/principles.yaml and formats/ unchanged.
  2. Write a profile (see the table below): a strength for every active rule, a resolution for every tension, your ranked aims and your scope.
  3. Run the build; fix what it reports.
  4. Write local notes for your tools and workflow.
A profile chooses Profile field
The strength of every active rule strengths
Where a choice comes from, if it is documented basis
Which rule wins in each tension precedence
Ranked aims aim_order
The format, dialect and accepted extensions of the version of record scope.encoding
The treatment of a category of printed mark, where it departs from the derived one scope.marks
Source types not covered scope.unsupported_sources

A profile has status draft until every strength is a confirmed choice. In a draft, a rule without a basis entry is a core default and is reported as unconfirmed.

A project that wants an extra normalisation, rule or format feature proposes it for the registry. This keeps the list of normalisations closed.

Reading the source (read)

What is read from the source and transcribed.

Theme Rule Statement openscore-2026-11 sos-2026-11 Relations
Fidelity read.preserve-distinctions Preserve the distinctions the source makes. Where the source uses different notations for what might seem the same, keep the difference (for example common time, cut time and 4/4; ties and slurs; acciaccatura and appoggiatura; key signatures as given). MUST MUST formats fmt.phrase-slur-tie, fmt.time-signature-symbol, fmt.grace-timing
Fidelity read.consistency-by-equivalence Consistency means equivalence only. Encode notations that mean the same thing the same way. Fidelity read.preserve-errors Source errors are preserved. Transcribe a source error as printed and record it as an observation. Never fix it silently in the transcription. SHOULD MUST refines stance.judgement-stays-out; requires declare.observations; see also declare.report-deviations, correct.error-test; formats fmt.irregular-measures, fmt.annotations
Fidelity read.record-source-marks Record the source's own editorial marks. Brackets and similar marks printed in the source signal an intervention by that edition. Keep the printed mark in the encoding where the format expresses it, and record each such mark in the report. Where the format cannot express the mark, record it in the report only. MUST MUST see also declare.report-deviations; formats fmt.editorial-accidentals

MUST MUST requires declare.report-deviations; formats fmt.fingering
Terms and text read.source-language Keep the source language. Keep musical terms and other text in the source language. Translations are additions. MUST MUST tension with read.standard-instructions; see also declare.mark-additions, normalise.terms
Terms and text read.standard-instructions Standard encodings for instructions. Transcribe printed techniques, strings, mutes and harmonics using the standard encoding where one exists, even where that changes the printed wording. MUST MUST -
Notation read.composer-led-grouping Preserve composer-led grouping. Preserve beaming, rest and similar grouping that carries musical meaning (the composer's own choice for a passage). Grouping that is only the source edition's habit is a presentation matter. If the two cannot be told apart, keep the grouping as printed and record an observation. SHOULD SHOULD exception of normalise.beam-grouping, normalise.rest-grouping
Notation read.ornaments-as-printed Ornaments as printed. Copy ornaments as printed, including the difference between acciaccatura and appoggiatura and the position before or after the main note. Where the tool cannot represent a detail, use the nearest available form in this order - type of ornament, then number of beams or strokes, then other indications. MUST MUST formats fmt.grace-timing, fmt.ornament-realization
Notation read.ambiguous-marks Ambiguous marks. Where a printed mark could be read in more than one way (what it is, or which notes it attaches to), encode the reading that the source's own convention fixes - a curve joining adjacent notes of the same pitch is a tie, any other curve is a slur - attached to the notes at the horizontal positions nearest the printed endpoints. Where the convention does not fix a reading, encode that nearest-endpoint reading and record an observation that names the alternatives. A mark that cannot be read as any notated object is recorded as an observation and not encoded. MUST MUST refines stance.doubt-means-preserve; see also read.preserve-distinctions, declare.observations; formats fmt.phrase-slur-tie, fmt.spanner-geometry

The one kind of editorial intervention that a profile may allow, the test it must pass, and how it is recorded.

Notes for Transcribers

Local notes for transcribers and reviewers. Version 2026-11. Generated from notes/registry.yaml. Applies the profile sos-2026-11 of the Transcription Principles, version 2026-11. Part of the Scores of Scores document set (see the README).

These Notes say how our project works with the Transcription Principles: house style, tool settings, workflow, report format and suggestions for downstream editorial work. They are the local-notes layer for the Scores of Scores profile (sos-2026-11). Rules in the core are cited by ID, for example read.preserve-errors; the full list, with the strength each has in each profile, is the rules table. What each format can express is in Format support. These Notes replace the previous Transcription Guide (superseded; it survives in the repository history).

How to read these Notes

  • Notes narrow, never override. If a Note conflicts with a core rule or with the profile, the rule and profile win, and the Note is corrected. A Note can never add a normalisation (normalise.closed-list).
  • Every Note has a kind:
  • presentation: a choice among the normalisations the profile permits.
  • tool: settings and palette entries that may change between apps and versions.
  • house: a house convention (placement, scope, workflow, report format).
  • editorial: a suggestion for downstream editorial work. It is never applied in the version of record (VoR).
  • Each Note has a permanent ID, <area>.<slug>, and may say which core rules it applies to. Earlier section-and-number codes from the previous guide are kept as aliases and listed in the concordance at the end.
  • A point that no rule or Note covers is kept as printed and recorded as an observation (workflow.unclear-cases).
  • This document is generated from notes/registry.yaml by python3 tools/build.py. Edit the registry, not this file.

Metadata (metadata)

Whether and where metadata appears in the rendered score is project specific and handled at the templating stage. For stored metadata, more is more.

metadata.title-composer-lyricist: Title, composer and lyricist

house

Title and composer are present in the score properties and displayed. Title is at the top of the page, centred; composer is at the right-hand side, just below the title. For songs, the lyricist is at the left-hand side, just below the title, roughly in line with the composer.

Earlier codes: M1.

metadata.dedication: Dedication

house

Use a separate vertical frame above the main title frame, centred and italicised, at the templating stage.

Earlier codes: M2.

metadata.dates-not-shown: Dates are not shown

house

Birth and death dates are not shown for anyone (composer, lyricist or dedicatee). Some of that data is stored separately in the project data.

Earlier codes: M3.

metadata.composition-date: Date of composition

house

The date of composition is not shown in the title frame. A date and place of composition may be shown at the end of the score if it appears in the source.

Earlier codes: M4.

metadata.provenance-stored: Provenance is stored, not rendered

house; applies declare.record-provenance

Provenance (source edition and file, pages, transcriber, reviewer, licence, tools, and the Principles, profile and Notes versions) is stored in the project data and not rendered by default. The editorial report repeats the source details.

Earlier codes: M5.

Layout (layout)

Source breaks and placement above and below the stave.

layout.source-breaks: Entering source breaks

tool; applies encode.layout-as-data

Follow the source's system breaks first and page breaks second. Enter them with the app's standard break elements (not spacers or manual position offsets) so that removal is a single operation. Never split a bar across a break.

  • Omit all breaks in extreme cases (very small pages, or music transcribed from parts) and say so in the report.

Earlier codes: L1, L1.1, L1.2.

layout.above-below: Above and below the stave

house

Use the template defaults. Above the stave go tempo marks and playing instructions such as pizz. and arco. Below go all dynamics, hairpins and expression text.

  • Exception: Quartets: where one voice is arco and another pizz., place each above or below as suits its voice.

  • Exception: All: with several expressive markings at once, it can help to flip some to the other side.

  • Exception: Lieder: dynamics in the vocal parts go above.

Earlier codes: L2, L2.1, L2.2.

Rhythm and grouping (rhythm)

Beaming, rests, tuplets, tremolo and tempo.

rhythm.beaming-default: Default beaming

presentation; applies normalise.beam-grouping

Enter notes with the default beaming for the time signature. Editorial conventions for 6/8, for example, vary between editions, so they are normalised.

Earlier codes: T2, T2.2.

rhythm.beam-placement: Beam placement

house

Beams go all above or all below the noteheads, not a combination of both.

  • Exception: String parts never use beams with noteheads on both sides. Lieder piano parts sometimes need it, for example when crossing between treble and bass of the grand stave.

Earlier codes: T2.1.

rhythm.composer-led-signals: Telling composer-led grouping from house style

house; applies read.composer-led-grouping

Copy a non-standard grouping when it appears to be the composer's own choice for a passage (Bartok is a classic case). If you cannot tell, keep the source grouping and record an observation (read.composer-led-grouping).

  • Signals of composer-led grouping: it departs from the norm only in that passage; it recurs identically when the material recurs; it plainly serves the music (regrouping the metre, showing a phrase); or other sources agree.

  • Signals of house style: the same habit applies across the whole edition regardless of the music.

Earlier codes: T2.2.1.

rhythm.beam-across-break: Beams across a system break

tool; applies encode.layout-as-data

Do not copy a beam that would continue across a barline at a system break if the app has no provision for it. Separate the beam groups at that barline.

Earlier codes: T2.2.2.

rhythm.rest-grouping: Rest grouping

presentation; applies normalise.rest-grouping

Use the time-signature defaults. This can diverge visibly from the source; that is fine if consistent. State it once in the report.

Earlier codes: T3.

rhythm.tuplet-settings: Tuplet settings

tool; applies normalise.tuplet-brackets

Use the default bracket whatever the source uses. In the Inspector set Direction = Auto, Number type = Number and Bracket type = Auto.

  • In a long passage that is consistently in one tuplet, show the first marking and make the rest invisible. They stay in the file, so playback and export are unaffected.

Earlier codes: T4, T4.1, T4.2.

rhythm.tremolo-default: Tremolo

presentation; applies normalise.tremolo

Prefer the app's default form of a measured tremolo.

Earlier codes: T5.

rhythm.tempo-marks: Tempo marks

house; applies read.source-language

Include tempo marks as in the source, with metronome marks, above the stave. Keep tempo terms in the source language, with a bracketed translation for non-standard ones (text.translation-format). Gradual changes (rit., accel.) are lines and follow dynamics.terms and dynamics.ritardando-line.

Earlier codes: T6.

Clefs and stems (clef)

Which clefs to keep, adapt or replace.

clef.decision-order: Decision order for viola and cello

house; applies normalise.clef

(a) Keep the source clef where clef.preserved-clefs lists it. (b) Apply the leger-line test in clef.leger-line-test to brief changes. (c) Use clef.other-clefs-modern for any clef not listed.

clef.two-clefs-default: Two clefs by default

house

Most work is set in two clefs, treble and bass.

Earlier codes: C1.

clef.preserved-clefs: Clefs to preserve

house; applies normalise.clef

Preserve these clefs, subject to clef.leger-line-test. Lieder: treble clef with 8 beneath it (down an octave), typical for the tenor voice in modern editions (solo and choral). Viola: mostly alto clef, with occasional treble passages. 'Cello: bass, tenor and treble.

  • Exception: Cello treble clef is notated at the sounding octave, per modern convention. Some sources (for example Dvorak and Beethoven) use a de facto treble clef an octave lower; we avoid that practice.

Earlier codes: C2, C2.1, C2.2, C2.3.

clef.leger-line-test: Leger-line test for brief clef changes

presentation; applies normalise.clef

Omit or adapt brief clef changes where a source seems to prioritise page space over readability. For viola and cello, change clef only if you would need more than 2 leger lines and the passage stays high long enough to help the player. Use the clef a modern player would expect, and report it.

  • Some transcribers use the original clefs while transcribing (see workflow.original-clefs). An algorithmic approach to modern clef choice exists in the Species corpus and may be formalised later.

Earlier codes: C3.

clef.other-clefs-modern: Other clefs to modern equivalents

presentation; applies normalise.clef

Adapt any clef not listed in clef.preserved-clefs (soprano, mezzo-soprano, baritone, French violin clef) to its nearest modern equivalent. The cello clefs in clef.preserved-clefs are preserved.

Earlier codes: C4.

clef.no-stem-flips: No manual stem flips

tool; applies encode.defaults-not-overrides

Almost never flip a note's stem manually. This also matters for transposition and clef changes.

Earlier codes: C5.

dynamics.terms: Terms

presentation; applies normalise.terms

Copy the source, except where an alternative is clearly equivalent and more standard today (for example diminuendo or dim. for decrescendo).

dynamics.abbreviations: Abbreviations

presentation; applies normalise.terms

Use the recognised standards cresc., dim., rit., rall. and accel. Spell out anything even slightly ambiguous, or adapt it to one of these.

dynamics.spread-words-line: Words spread over several bars

tool; applies normalise.spread-words

For cre - - - scen - - - do across bars or systems, use a wide-dashed line (Line Thickness = 0.12sp, Dash Line Length = 5, Dash Gap Width = 20) with standard Begin text and a Continue text in parentheses at the start of each system, for example (dim.).

tool; applies encode.real-objects

Ties and slurs (ties)

tool; applies normalise.accidental-conventions

An accidental is not repeated at the start of the second (or later) bar of a tie, even at a system or page break. If the same pitch recurs later in that bar, the accidental is shown (a default, and worth keeping).

Brackets (brackets)

Our brackets, the source's brackets, and telling them apart.

brackets.ours: Square brackets mark what we add

house; applies declare.mark-additions

Square brackets in our files mark only what we add (accidentals, translations). Every other intervention is reported, not marked.

house; applies read.record-source-marks

In a direct transcription, keep the brackets (square or curved) that the source prints around a note, accidental or similar, as printed where the encoding expresses them, and otherwise record them in the report. Workflow (workflow)

How work proceeds from first transcription to release.

workflow.red-text: Red text while working

house; applies declare.report-deviations, declare.observations

While transcribing, use red staff text to explain an intentional deviation from the source and to mark anything suspicious, including a correction you did not make. Before release, convert each red text into a report entry (declare.report-deviations) or an observation (declare.observations), then delete it. A release contains no red text.

Earlier codes: W1, W2.

workflow.source-errors: Handling a suspected source error

house; applies read.preserve-errors, correct.error-test

Transcribe it as printed, mark it with red text while working, and record an observation in the report (declare.observations, editorial.observations). If the error passes the clear-error test (correct.error-test), the observation names the one minimal change, so that a correction can be recorded (correct.record).

Earlier codes: W3.

workflow.consistency-edits: Consistency edits

house; applies read.consistency-by-equivalence, declare.observations

Make equivalent notations match, but do not edit a divergence that might be musical (an articulation that differs in one part, a different pitch in a recurring motive). Preserve it and record an observation (declare.observations). Harmonising is editorial.

Earlier codes: G4.

workflow.unclear-cases: A case no rule or Note covers

house; applies stance.doubt-means-preserve, declare.observations

Keep what the source prints and record an observation (stance.doubt-means-preserve, declare.observations). Topics listed under "Outside this version" have no Note yet and are handled this way.

workflow.manuscripts: Manuscripts

house

Manuscripts and other special sources are out of scope for this profile (unsupported_sources in the profile) and are not transcribed under it.

Some transcribers use the original clefs while transcribing, to make proofreading easier (comparing a notehead on the same line or space). Before release the clefs follow clef.preserved-clefs, clef.leger-line-test and clef.other-clefs-modern.

The editorial report (report)

What the report contains and how it is laid out.

report.contents: What is reported

house; applies declare.report-deviations

Report any deviation from the source that is not visibly marked in the score. The report covers at least the following.

  • Consistency edits within read.consistency-by-equivalence.

  • Normalised terms and abbreviations.

  • Added accidentals (also bracketed in the score).

  • Clef changes and modernisation.

  • Grouping kept as printed because composer-led and house-style grouping could not be told apart (as an observation).

  • System and page breaks omitted.

  • Ornaments or details entered in the nearest available form.

  • Excluded categories of mark.

  • Observations, in a separate section (declare.observations).

  • Which brackets are ours, where the source also uses square brackets (brackets.tell-apart).

Earlier codes: R1.

report.systematic-vs-specific: Systematic and specific entries

house; applies declare.report-deviations

State systematic differences once, in a general note that lists the normalisations applied. Give each specific intervention one row, with bar, part or staff, source reading, our reading, reason and rule ID.

  • Example: A clef is changed in a cello part. b. 34, Vc.: clef changed to tenor; passage stays above the stave for 9 bars (clef.leger-line-test).

Earlier codes: R2.

report.header: Report header

house; applies declare.record-provenance

Source edition and file, pages, transcriber, reviewer, date, the app and version, the Principles version, the profile, the Notes version, and the normalisations applied (also recorded in the transcription's machine-readable metadata, the sidecar).

Earlier codes: R3.

report.purpose: Purpose of the report

house; applies declare.report-deviations

The report is for readers who need to know how the score differs from its source. It should be possible to read the score without the report, and to recover what the source prints from the two together.

Earlier codes: R5.

Editorial matters (editorial)

Out of scope for the transcription and the version of record. Suggestions for handing observations on and for downstream work.

editorial.observations: Observations

editorial; applies declare.observations

If you notice something that looks like a source error, a divergence between parts or repeated passages, or a question an editor would want to ask, record it as an observation in a separate section of the report, not in the score. Say where it is, what the source prints, and why it caught your eye. Observations are not decisions. An observation about a clear error (correct.error-test) names the one minimal change.

Earlier codes: E1, R4.

editorial.do-not-resolve: Do not resolve

editorial; applies stance.judgement-stays-out

Do not choose between readings, supply missing material or "improve" the score. A correction is made only for a clear error (correct.error-test), and only where the profile allows it.

Earlier codes: E2.

editorial.downstream-editions: Downstream editions

editorial; applies stance.judgement-stays-out

Anyone preparing an edition (harmonising recurring motives or articulation across parts, adding suggested accidentals, choosing between sources, dropping the source's own brackets) should start from a pinned VoR version, work in their own project, and report every change there. Use an established scheme to record the interventions, such as the editorial markup in MEI or TEI. The previous guide's consistency edits, 'obvious' corrections and editorial accidentals belong at this layer.

Earlier codes: E3.

editorial.collation: Collating sources

editorial

A collation records where transcriptions of the same work differ, without choosing between them. It is a derived view and never part of a transcription. Editions may use it as a starting point.

Earlier codes: E4.

Outside this version

These topics have no Note in this version. The core rules apply to them unchanged: keep what the source prints (stance.doubt-means-preserve) and record an observation (declare.observations). A later pinned version adds Notes for them.

  • Lyrics: underlay, hyphenation, melismas, translations.
  • Piano pedalling.
  • Articulations, fermatas, repeats and voltas.
  • Rehearsal marks, bar numbering, multi-bar rests.
  • Hairpins (beyond their placement in layout.above-below).
  • Ornaments other than grace notes (trills, turns, mordents).
  • Courtesy accidentals already in the source.

Glossary

Generated from core/glossary.yaml. The same terms are used in the rules, the Notes and the paper.

Term Meaning
Source The notated document being transcribed, one edition or one manuscript, identified by file and pages.
Transcription The digital encoding of one source, made under a profile. Also the name of the tier of decisions that need no judgement and no second source.
Encoding A file or set of files that records a transcription in one format.
Format A specification that defines how music is encoded (KRN, MusicXML, MEI, MuseScore's native MSCX). A format sets what can be expressed. It is not the same as an application that reads or writes it.
Application A program such as MuseScore, whose defaults act as a house style that the format does not set.
Version of record (VoR) The exact transcription of one source, errors included, identified by a pinned version.
Tier One of three kinds of decision. Transcription needs no musical judgement and no second source. Presentation is systematic, reversible and changes nothing notated. Editorial needs judgement or another source.
Normalisation A registered presentation choice such as beam grouping or clefs. The list is closed.
Profile A project's choices over the core rules, the format of its version of record, and the treatment of marks. In the paper a profile is also called a position.
Strength MUST, SHOULD, MAY or OFF (BCP 14). MUST is always applied, SHOULD unless there is a recorded reason, MAY at discretion, OFF not adopted. For a normalisation or a correction, OFF means not permitted.
Format feature One entry in the formats data (fmt.*) that states, for each of four formats, whether and how it can express something, and on what evidence.
Status The capability label of a format feature cell. Direct, qualified, extension, workaround or unknown. It is not a quality score.
Unsupported The treatment of a category of printed mark that the profile's format cannot express. Derived from the formats data. It is a limit of the format, not a judgement, and changes when the format or the profile does.
Observation A point recorded in the report (a possible source error, a divergence, a mark with more than one reading, an unclear tier). It does not change the transcription.
Clear error A source error that passes the two-part test in correct.error-test. Every other error is kept as printed.
Correction A change to the printed reading of a clear error, made either in the transcription (correct.in-place) or in a separate layer (correct.layer), and always recorded (correct.record).
Corrections layer A layer separate from the transcription, pinned to a transcription version, that records corrections. The corrected view is derived from the transcription and the layer.
Note kinds Presentation (a choice among permitted normalisations), tool (settings that may change between applications), house (a house convention) and editorial (a suggestion for downstream work, never applied in the version of record).
Sidecar The machine-readable metadata stored with each transcription: source, pages, tools, versions and the normalisations applied.
Collation A derived record of where transcriptions of the same work differ, without choosing between them.
Fixture A defined test situation that exercises format features and, for the worked examples, rules. A feature cell counts as tested only when a fixture covering it has a recorded result for that format.
